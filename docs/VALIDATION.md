# Validation

Этот файл описывает финальную (текущую) схему валидации, которую мы считаем основной для принятия решений по моделям.

## Термины

- `holdout`: данные, которые в конкретном прогоне не участвуют в обучении, только в проверке.
- `holdout-triplet`: одна тройка holdout-мышей (`control + endo + exo`).
- `battery`: набор многих holdout-triplet прогонов.
- `manifest`: фиксированный список holdout-triplet, который используем в сравнении.
- `dev`: часть manifest для выбора кандидата.
- `lock`: часть manifest для независимой проверки выбора.
- `worst-slice`: худший из обязательных стресс-срезов (`full-region` и `cerebellum-stress`).

## 1) Зачем у нас сложная валидация

Для этой задачи есть типичные риски:

- мало групп (`mouse`) и высока чувствительность к составу holdout;
- легко получить "красивый" результат на одном удобном сплите;
- много гипотез => риск случайно выбрать нестабильного лидера.

Поэтому мы валидируем не одним числом, а каскадом проверок.

## 2) Что считаем базовой метрикой

Основная метрика:

- `macro_f1` (primary).

Дополнительно всегда смотрим:

- `balanced_accuracy`,
- `accuracy`.

Причина: `macro_f1` лучше отражает баланс по 3 классам, а `balanced_accuracy` помогает поймать перекосы по классам.

## 3) Финальный протокол валидации (по шагам)

### Шаг A. Group-aware обучение и локальный holdout

На уровне отдельных run:

- сплиты строятся group-wise по `mouse` (без смешивания train/val по одной мыши);
- используется `stratified_group_kfold` для CV-части;
- есть явный local holdout по заданным группам.

Это базовая защита от утечки между train и validation: модель не видит спектры той же мыши и в обучении, и в проверке одновременно.

### Шаг B. Battery по множеству holdout-triplet

Здесь `battery` означает "набор многих независимых проверок", а не один тест.

Одна проверка (`holdout-triplet`) строится так:

- в holdout кладем ровно 3 мыши: одну из `control`, одну из `endo`, одну из `exo`;
- все остальные мыши идут в train/CV для этого прогона;
- считаем метрики на этих 3 holdout-мышах.

Потом повторяем это для многих разных троек мышей.

Пример:

- сплит 1: (`mk1`, `mend2`, `mexo3`);
- сплит 2: (`mk2`, `mend1`, `mexo1`);
- сплит 3: (`mk3`, `mend4`, `mexo2`) и т.д.

Так мы получаем не одну оценку, а распределение качества на разных составах holdout.  
Первый агрегат этого шага — `all-holdouts`, то есть средние метрики по всем доступным тройкам.

### Шаг C. Balanced manifest (обязательный)

Чтобы не выиграть случайно на "удобных" сплитах, строим сбалансированный поднабор holdout-triplet с квотами:

- минимальная доля `full-region` holdout (в triplet представлены все 3 региона мозга),
- минимальная доля `cerebellum-stress` holdout (есть мышь, представленная только `cerebellum`),
- минимальная доля `mk3-control` стресс-сплитов (в control-holdout участвует `mk3`).

И сравнение кандидатов делаем не только на `all`, но и на этом `balanced` поднаборе.  
Идея в том, что `balanced`-ветка специально усиливает сложные сценарии, где обычно проявляется нестабильность моделей.

### Шаг D. Region-aware срезы (обязательные)

Для каждого кандидата считаем не только общий `overall`, но и отдельные срезы:

- `full-region holdouts`,
- `cerebellum-stress holdouts`,
- `worst-slice` = минимум из двух срезов выше.

Кандидат не принимается по одному `overall`, если он слаб в `worst-slice`: это защита от ситуации, когда модель выглядит сильной в среднем, но системно проваливается на более сложных срезах.

### Шаг E. Dev/Lock внутри balanced battery

Сбалансированный manifest делим на:

- `dev` (для выбора),
- `lock` (для независимой проверки выбора).

Разделение делается со стратификацией по ключевым stress-флагам, чтобы в обеих частях были важные типы сплитов.  
Таким образом, выбор стратегии делается на `dev`, а подтверждение устойчивости этого выбора — на `lock`, который не участвует в самом выборе.

### Шаг F. MK3 gate (safety)

На `lock` добавлен дополнительный safety gate:

- если стратегия существенно хуже fallback на `mk3-control` срезе, она не может быть финальным победителем.

Это защита от деградации на чувствительном хвостовом сценарии: даже при хорошем среднем качестве стратегия не проходит, если она нестабильна в этом контрольном стрессе.

### Шаг G. Multi-seed sweep

Dev/Lock запуск повторяется на диапазоне seed (а не один раз), после чего смотрим:

- частоту побед (`winner counts`),
- стабильность выбора (`dev_lock_agree_rate`),
- средние/медианы `lock_overall` и `lock_worst_slice`.

Итоговый вывод делаем по устойчивости, а не по одному запуску: нам важнее повторяемый результат, чем единичный "удачный" seed.

## 4) Почему именно так

Почему этот протокол для нас оптимален:

- сильно снижает риск переобучения на единичный holdout;
- учитывает region- и stress-структуру данных;
- остается практичным по времени для хакатона;
- воспроизводим: все этапы формализованы отдельными скриптами и CSV-артефактами.

## 5) Минимальный набор артефактов, по которым принимаем решение

При сравнении кандидатов фиксируем:

- summary по `all-holdouts`,
- summary по `balanced-holdouts`,
- `dev/lock` comparison/decision,
- `multi-seed` winner counts + per-strategy summary.

Если есть конфликт, приоритет у более строгого блока:

1. `lock + worst-slice + mk3-gate`,
2. затем `balanced`,
3. затем `all`.

## 8) Что важно помнить

- Валидация в этом проекте — это не один CV-score, а многоступенчатый протокол.
- Решение принимаем по стабильности на строгих срезах, а не по максимальному единичному числу.
- Любая новая гипотеза должна проходить этот же протокол, иначе её результат считаем предварительным.
