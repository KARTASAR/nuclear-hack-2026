# Варианты реализации пайплайна под `data/real` (с оценками 0–10)

Этот документ описывает практические варианты, как реализовать код для работы с текущими реальными данными.  
Оценка `0..10` — общий приоритет варианта с учётом: качества результата, времени внедрения, рисков.

## Вариант 1. Быстрый baseline: `center1500`, усреднение по карте, классический ML

Идея:

- взять только `center1500`;
- каждый `.txt` файл превратить в один усреднённый спектр (mean по 525 точкам);
- обучить простой multiclass baseline (например, SVM/LightGBM).

Плюсы:

- очень быстро запустить;
- легко дебажить;
- минимальные вычислительные затраты.

Минусы:

- сильная потеря информации (пространственная структура карты теряется);
- не используется `center2900`.

Оценка: **7/10**  
Когда выбирать: если нужен быстрый «рабочий ноль» за 1 день.

## Вариант 2. `center1500`, обучение по всем точкам карты (point-level)

Идея:

- sample = точка `(X, Y)`;
- использовать все 525 спектров из каждого файла;
- делать split строго по животному/карте, чтобы не было leakage.

Плюсы:

- максимальный объём обучающих примеров;
- выше шанс получить сильное качество, чем у усреднения.

Минусы:

- высокий риск leakage при неправильном split;
- больше требований к RAM/времени;
- сложнее аккуратно валидировать.

Оценка: **8/10**  
Когда выбирать: если есть время сделать корректную групповую валидацию.

## Вариант 3. Два независимых пайплайна (`center1500` и `center2900`) + ансамбль на уровне вероятностей

Идея:

- обучить две модели отдельно для каждого окна;
- объединять предсказания (mean logits / weighted average).

Плюсы:

- использует оба окна без сложного «сшивания» спектров;
- относительно устойчиво к несовпадению сеток wave.

Минусы:

- нужно поддерживать два пайплайна;
- калибровка ансамбля добавляет сложность.

Оценка: **8.5/10**  
Когда выбирать: если цель — сильное качество при умеренной сложности.

## Вариант 4. Сшивка `center1500 + center2900` в единый вектор на sample

Идея:

- для парных измерений строить единый спектральный вектор (через интерполяцию и конкатенацию двух окон).

Плюсы:

- единая модель на полной доступной спектральной информации;
- потенциально лучше интерпретируемость (один feature-space).

Минусы:

- сложнее реализация;
- нужно аккуратно матчить пары файлов и обрабатывать аномалии (`Average`, mislabel center).

Оценка: **7.5/10**  
Когда выбирать: если команда готова к более аккуратному data engineering.

## Вариант 5. MIL/иерархическая модель: точка -> карта -> класс

Идея:

- рассматривать карту как «мешок» спектров (multiple instance learning);
- модель учится агрегировать точки внутри карты.

Плюсы:

- естественно для структуры данных;
- часто даёт хороший компромисс между качеством и устойчивостью.

Минусы:

- самая сложная инженерно/модельно реализация;
- выше риск не успеть на хакатоне.

Оценка: **6.5/10**  
Когда выбирать: если есть опыт и запас времени.

## Вариант 6. Минимальные правки текущего кода + бинаризация классов (не рекомендуется)

Идея:

- сохранить текущую бинарную архитектуру, сведя 3 класса к 2 (например, `control` vs `endo+exo`).

Плюсы:

- почти мгновенный старт на существующем коде.

Минусы:

- не соответствует исходной постановке с 3 классами;
- ограниченная ценность результата.

Оценка: **3/10**  
Когда выбирать: только для технического smoke-test инфраструктуры.

## Рекомендуемый путь (практично для хакатона)

1. Сначала сделать Вариант 1 как sanity baseline.  
2. Затем перейти на Вариант 3 (два окна + ансамбль).  
3. Если останется время — прототип Варианта 4 или 5.

Итого по приоритету:

1. Вариант 3 — **8.5/10**  
2. Вариант 2 — **8/10**  
3. Вариант 4 — **7.5/10**  
4. Вариант 1 — **7/10**  
5. Вариант 5 — **6.5/10**  
6. Вариант 6 — **3/10**
