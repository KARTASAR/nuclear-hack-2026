# Конкретный план: как двигаться сейчас (эксперименты + архитектура кода)

Цель: быстро запускать много гипотез, не ломая кодовую базу, и сохранять полную воспроизводимость каждого прогона.

## 1. Что делаем прямо сейчас

1. Делаем **минимальный рабочий baseline-pipeline** для `center1500`.
2. Сразу проектируем его как **конструктор взаимозаменяемых блоков** (парсер, препроцессинг, агрегация, модель, валидация, метрики).
3. Вводим **жёсткий трекинг экспериментов** с конфигом, метриками и артефактами.
4. После baseline масштабируемся на:
- `center2900`;
- dual-window (2 модели + ансамбль);
- point-level vs file-level vs mouse-level подходы.

## 2. Принципы, которых держимся

1. Конфиг-ориентированность: любой эксперимент задаётся конфигом, не правкой кода.
2. Воспроизводимость: каждый запуск можно повторить из `run_id + config + commit`.
3. Изоляция блоков: preprocessing/модель/splitter/aggregation меняются независимо.
4. Без leakage: split только group-wise (по `mouse` или более строгой группе).
5. Быстрый цикл: сначала дешёвые эксперименты, потом дорогие.

## 3. Предлагаемая структура кода (можно не опираться на текущую)

## 4. Интерфейсы блоков (идея)

Каждый блок должен иметь общий интерфейс:

- `DataBuilder.build(config) -> DatasetBundle`
- `Preprocessor.fit/transform`
- `Model.fit/predict_proba`
- `Splitter.split(X, y, groups)`
- `Runner.run(experiment_config) -> RunResult`

Это позволит менять, например, `arPLS -> morphological baseline` или `SVM -> ResNet` без переписывания остального пайплайна.

## 5. Эксперимент-трекинг: что обязательно сохраняем

Для каждого запуска (`run_id`) сохраняем:

1. `config_resolved.yaml` (полный финальный конфиг).
2. `git_commit`, `dirty_state`, время запуска.
3. `data_snapshot.json`:
- список входных файлов;
- исключения (`Average`, аномалии);
- хеши/размеры (минимум контроль целостности).
4. Метрики:
- общие (`macro_f1`, `balanced_accuracy`, `auc_ovr`, `accuracy`);
- по фолдам;
- по классам.
5. `predictions.csv` (OOF или val preds + true labels + group id).
6. Короткая `notes.md`: что меняли и гипотеза эксперимента.

Минимальный реестр запусков:

- `runs/registry.csv` (или `registry.parquet`) с колонками:
`run_id, parent_run, date, owner, hypothesis, config_hash, commit, key_metrics, status`.

## 6. Конкретный план по шагам (порядок работ)

### Этап A (сегодня): фундамент

1. Зафиксировать единый data index по `data/real`:
- class, mouse, region, center, file_path, flags (average/anomaly).
2. Описать правила фильтрации:
- `*_Average.txt` вне основного train;
- аномальный файл `center2900` с диапазоном `1500` — отдельный флаг/исключение.
3. Реализовать базовый runner + сохранение `run_id` артефактов.

Результат этапа A: можно гарантированно повторить любой запуск.

### Этап B: baseline-волна (быстрые эксперименты)

1. `center1500`, file-level mean spectrum, SVM.
2. `center1500`, point-level, SVM.
3. Сравнение preprocessing сетки:
- baseline: `airPLS` vs `arPLS`;
- normalization: `SNV` vs `MSC` vs `EMSC`.
4. Выбрать лучший быстрый baseline по `macro_f1`.

Результат этапа B: рабочая опорная точка качества + стабильный pipeline.

### Этап C: расширение

1. Повтор этапа B для `center2900`.
2. Dual-window ансамбль:
- отдельные модели для `1500` и `2900`;
- объединение вероятностей.
3. Если модели обучаются быстро: добавить 1-2 DL варианта.

Результат этапа C: основной кандидат решения для финала.

### Этап D: финализация

1. Зафиксировать top-N запусков.
2. Проверить воспроизводимость повторным прогоном лучшего `run_id`.
3. Подготовить таблицу для презентации:
- гипотеза -> изменение -> метрики -> вывод.

## 7. Матрица первых экспериментов (что именно менять)

Минимальный набор для старта:

1. Уровень sample: `file_mean` vs `point`.
2. Baseline: `airPLS` vs `arPLS`.
3. Normalization: `SNV` vs `MSC` vs `EMSC`.
4. Model: `SVM` vs `LightGBM/XGBoost` (если быстро).
5. Window: `center1500` vs `center2900`.

Это даёт контролируемый сет из экспериментов без взрыва комбинаторики.

## 8. Критерии принятия решений

Переходим к следующему варианту, если:

1. Улучшение `macro_f1` статистически/практически заметно и стабильно по фолдам.
2. Нет признаков leakage.
3. Прогон воспроизводится из артефактов `run_id`.

Отбрасываем вариант, если:

1. Улучшение нестабильно между фолдами.
2. Конфиг/код трудно повторить.
3. Время обучения неадекватно приросту качества.

## 9. Что важно для презентации на хакатоне

Нужен не только «лучший score», но и история:

1. Какие гипотезы проверили.
2. Что сработало/не сработало и почему.
3. Как обеспечили корректность валидации.
4. Почему финальный pipeline выбран как инженерно и научно обоснованный.

Этот документ и run-реестр как раз дают эту историю в воспроизводимом виде.
