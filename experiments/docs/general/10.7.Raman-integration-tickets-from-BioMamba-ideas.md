# Raman Integration Tickets from the BioMamba Idea Mix

## Goal

Turn the useful pieces of the external BioMamba-style signal stack into a small set of implementation-ready Raman tickets that fit the current `main` branch.

This document is grounded in the following external files the user pointed at:

- `multitaper.py`
- `multitaper_quickstart.py`
- `test_multitaper.py`
- `spectro_temporal_embedding.py`
- `wtfm_block.py`
- `sector_decomposition.py`
- `mixture_of_experts.py`

The following files are intentionally **not** treated as first-wave port targets:

- `bidirectional_ssm.py`
- `complete_biomamba.py`
- `main_biomamba_pipeline.py`
- `tensor_decomposition.py`
- `sparse_feedforward.py`

## Selection Summary

The most transferable ideas are:

1. multi-taper PSD as a physically meaningful spectral frontend;
2. patching along the Raman axis instead of time;
3. dual-branch FFT / wavelet tokenization;
4. sector-aware routing, but simplified into spectral sectors rather than anatomical sectors.

The heavy Mamba / SSM / tensor-decomposition stack should not be ported in the first Raman wave.

## Recommended Implementation Order

1. Ticket 1: multi-taper frontend
2. Ticket 2: patch tokenizer with FFT / wavelet branches
3. Ticket 3: spectral sectors + lightweight MoE
4. Ticket 4: XAI hooks for input, patch, sector, and expert levels

This order keeps the engineering path simple and preserves clean ablations.

## Ticket 1

### Title

Add a reusable multi-taper Raman frontend and synthetic PSD validation

### Type

Feature / model building block / low-risk research transfer

### Priority

High

### Problem

The current Raman models in `src/raman_hack/models/torch_spectral.py` consume preprocessed intensity vectors directly. That is simple, but it does not exploit a more stable spectral-energy representation.

The external `multitaper.py` module contains the most immediately useful idea in the whole BioMamba mix:

- DPSS-based multi-taper PSD extraction
- configurable `NW`, taper count, adaptive weighting, DC removal
- explicit validation against synthetic frequency peaks and smoothing behavior

For Raman, this is attractive because it gives a physically interpretable energy-like frontend and naturally supports the energy-aware XAI metrics already described in [10.6.Domain-validation-and-physics-aware-Raman-XAI-smart-ticket.md](./10.6.Domain-validation-and-physics-aware-Raman-XAI-smart-ticket.md).

### Current Branch Constraints

- The current training stack is PyTorch, not JAX/Flax.
- The runner expects models to be built through `build_torch_spectral_model(...)`.
- The repo already has stable config and test conventions under `src/raman_hack/config.py`, `configs/experiment/*`, and `tests/*`.

So this should be a **PyTorch-native reimplementation**, not a dependency bridge to the external JAX code.

### Proposed Scope

- add a reusable `RamanMultiTaperEmbedding` module in PyTorch;
- support both full-spectrum and patch-level usage;
- expose configuration for `NW`, `n_tapers`, `adaptive`, `remove_dc`, and output bin count;
- make the module usable as a frontend for later patch-transformer and MoE tickets;
- add synthetic tests modeled after `test_multitaper.py`.

### Proposed File Touches

```text
src/
  raman_hack/
    models/
      raman_frontends.py
      __init__.py
      torch_spectral.py

tests/
  test_raman_multitaper.py

configs/
  experiment/
    raman_mt/
      mt_1500_smoke.yaml
      mt_2900_smoke.yaml
```

### Proposed API

```python
class RamanMultiTaperEmbedding(nn.Module):
    def __init__(
        self,
        n_freq_bins: int | None = None,
        emb_channels: int = 64,
        mt_nw: float = 3.0,
        mt_n_tapers: int = 5,
        mt_adaptive: bool = False,
        mt_remove_dc: bool = True,
    ) -> None:
        ...

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        # x: (B, 1, N)
        # out: (B, C, F)
        ...
```

### Acceptance Criteria

- `RamanMultiTaperEmbedding` works in pure PyTorch and has no JAX runtime dependency.
- Output shape is stable for both `1500` and `2900` crops.
- Synthetic tests cover:
  - known peak localization;
  - DC suppression;
  - smoother output for larger `NW`;
  - no `NaN` / `Inf`.
- The module is importable through [__init__.py](../../src/raman_hack/models/__init__.py).
- At least one smoke config under `configs/experiment/raman_mt/` runs end-to-end through the current runner.

### Non-Goals

- Do not port the JAX module directly.
- Do not add MNE as a required dependency.
- Do not create a separate training pipeline just for the frontend.

## Scope

## Ticket 2

### Title

Add a patch-based Raman tokenizer with FFT and wavelet branches

### Type

Feature / model family / medium-risk research transfer

### Priority

High

### Problem

The external `spectro_temporal_embedding.py` and `wtfm_block.py` contain a strong idea that is more relevant to Raman than the full BioMamba backbone:

- patch the input signal;
- transform each patch into spectral features;
- fuse complementary views such as FFT magnitude and wavelet detail.

For Raman this maps naturally from time patches to **wavenumber patches**:

- patch = local Raman sub-spectrum;
- token = local band representation;
- attention / Grad-CAM can operate directly at patch level for band-level XAI.

### Proposed Scope

- add a `RamanSignalPatcher` that segments along the Raman axis;
- add an `RamanPatchFFTEmbedding`;
- add an `RamanPatchWaveletEmbedding`;
- add a small fusion module producing token sequences for either a transformer or a lightweight CNN head;
- register a new model family such as `raman_patch_transformer`.

### Proposed File Touches

```text
src/
  raman_hack/
    models/
      raman_frontends.py
      raman_patch_models.py
      __init__.py
      torch_spectral.py
    config.py
    runner/
      experiment.py

tests/
  test_raman_patch_tokenizer.py
  test_raman_patch_transformer.py

configs/
  experiment/
    raman_patch/
      rpt_1500_fft.yaml
      rpt_1500_fft_wavelet.yaml
      rpt_2900_fft.yaml
      rpt_2900_fft_wavelet.yaml
```

### Proposed API

```python
class RamanSignalPatcher(nn.Module):
    def __init__(self, patch_size: int = 64, stride: int = 16) -> None:
        ...


class RamanPatchFFTEmbedding(nn.Module):
    def __init__(self, hidden_dim: int = 128) -> None:
        ...


class RamanPatchWaveletEmbedding(nn.Module):
    def __init__(self, hidden_dim: int = 128, wavelet: str = "db4") -> None:
        ...


class RamanPatchTransformer(nn.Module):
    def __init__(self, n_classes: int, ...) -> None:
        ...
```

### Compatibility Notes

- Reuse the existing torch experiment runner.
- Add the new family to:
  - [config.py](../../src/raman_hack/config.py)
  - [torch_spectral.py](../../src/raman_hack/models/torch_spectral.py)
  - [experiment.py](../../src/raman_hack/runner/experiment.py)
- Keep patch outputs easy to inspect so they can later feed Part 1 / Part 2 XAI.

### Acceptance Criteria

- Patch extraction is deterministic and shape-stable.
- FFT-only and FFT+wavelet variants both run on `1500` and `2900`.
- The fused token sequence can be consumed by a transformer head.
- There are smoke tests for:
  - patch count and shape;
  - no shape regressions in fusion;
  - forward pass on a full batch.
- At least one run artifact exists for an FFT-only and a dual-branch config.

### Non-Goals

- Do not port the full WTFM block with 2D convolutions if a 1D wavelet branch is enough.
- Do not add Mamba / SSM in the same ticket.
- Do not hide patch-to-wavenumber mapping behind opaque indexing.

## Ticket 3

### Title

Add spectral-sector decomposition and a lightweight Raman MoE classifier

### Type

Feature / interpretable architecture / medium-risk research transfer

### Priority

High

### Problem

The external `sector_decomposition.py` and `mixture_of_experts.py` are too heavy in their original form, but they contain one idea worth porting:

- coarse, interpretable routing via sector summaries.

For Raman, "sector" should not mean anatomical EMG groups. It should mean **literature-grounded spectral regions** such as:

- protein-dominated bands;
- lipid-dominated bands;
- phenylalanine anchor band;
- CH-stretch bands in the `2900` window.

This is attractive because sector gates are interpretable by design and can later be validated with the band-level XAI layer.

### Proposed Scope

- add a `RamanSpectralSectors` block that aggregates features over predefined Raman ranges;
- add a small gating network driven by sector summaries;
- add a lightweight `RamanMoENet` with 2-4 experts;
- keep routing dense or top-k selectable, but avoid the full MoEMba complexity;
- store expert weights and sector gates in an auxiliary output for XAI.

### Proposed File Touches

```text
src/
  raman_hack/
    models/
      raman_moe.py
      raman_frontends.py
      __init__.py
      torch_spectral.py
    config.py
    runner/
      experiment.py

tests/
  test_raman_spectral_sectors.py
  test_raman_moe.py

configs/
  experiment/
    raman_moe/
      rmoe_1500_lite.yaml
      rmoe_2900_lite.yaml
```

### Proposed API

```python

        ...

    def forward(self, emb: torch.Tensor) -> tuple[torch.Tensor, torch.Tensor]:
        # sector_feats: (B, S, C)
        # sector_gates: (B, S)
        ...

    def __init__(self, n_classes: int, n_experts: int = 3, ...) -> None:
        ...

    def forward(self, x: torch.Tensor) -> tuple[torch.Tensor, dict[str, torch.Tensor]]:
        ...
```

### Compatibility Notes

- Sector definitions should be aligned with the band registries planned in [10.6.Domain-validation-and-physics-aware-Raman-XAI-smart-ticket.md](./10.6.Domain-validation-and-physics-aware-Raman-XAI-smart-ticket.md).
- The first version can use dense softmax routing; top-k sparse routing is optional.
- Expert outputs must be easy to inspect and stable to serialize.

### Acceptance Criteria

- A `RamanSpectralSectors` module exists and works on current crop lengths.
- Sector gates are returned for every forward pass.
- `RamanMoENet` runs with 2-4 experts through the existing torch training loop.
- The model can train with current class labels and current experiment runner.
- Sector gates and expert weights are available in the forward `aux` output.
- At least one `1500` and one `2900` smoke config run successfully.

### Non-Goals

- Do not port quantum-dimension estimation.
- Do not port Levin-Wen fusion logic.
- Do not require sparse top-k routing in the first merge.
- Do not introduce a full hierarchical MoE stack.

## Ticket 4

### Title

Add XAI hooks for Raman frontends, patch tokens, sectors, and experts

### Type

Feature / explainability integration / high-value follow-up

### Priority

High

### Problem

The value of Tickets 1-3 is not just better accuracy. Their main value is that they expose cleaner explanation units:

- multi-taper energy bins;
- patch tokens along the Raman axis;
- wavelet-scale channels;
- sector gates;
- expert routing weights.

Without explicit XAI wiring, these modules would become new black boxes rather than better scientific tools.

### Proposed Scope

- extend the explainability plan from [10.5.Physically-grounded-Raman-XAI-smart-ticket.md](./10.5.Physically-grounded-Raman-XAI-smart-ticket.md) so it can read:
  - input-spectrum attributions;
  - patch-level attributions;
  - sector-gate importances;
  - expert-gate importances;
- support Captum-style IG first;
- keep Grad-CAM support for CNN-compatible layers where available;
- add reporting that maps patch indices and sector ids back to physical Raman windows.

### Proposed File Touches

```text
src/
  raman_hack/
    explainability/
      adapters/
        raman_patch.py
        raman_moe.py
      aggregation/
        patch_mapper.py
        sector_mapper.py
      validation/
        concordance.py
        report_builder.py

tests/
  test_patch_xai_mapping.py
  test_sector_gate_reporting.py
  test_moe_xai_outputs.py
```

### Required Behaviors

- For patch models:
  - attribution can be aggregated per patch and mapped to wavenumber intervals.
- For sector models:
  - `sector_gates` can be exported directly as interpretable evidence.
- For MoE models:
  - `expert_gate_weights` can be saved and summarized by class.
- For validation:
  - sector-level and patch-level importances can be compared against band registries and energy-aware metrics.

### Acceptance Criteria

- IG can run on at least one new model family from Tickets 1-3.
- Patch-level attribution can be converted into Raman intervals.
- Sector gates can be exported in validation reports.
- Expert routing weights can be summarized per sample and per class.
- Validation outputs remain compatible with the `runs/<run_id>/interpretability/validation/` layout from Part 2.

### Non-Goals

- Do not block on LRP or GRASS in the first pass.
- Do not require Grad-CAM for models that do not expose a sensible convolutional target layer.
- Do not mix patch-level and sector-level reports without explicit mapping metadata.

## What Not to Port Now

These ideas should remain explicitly out of scope for the first Raman adaptation wave:

- bidirectional SSM / Mamba blocks
- tensor decomposition layers
- sparse FFN tricks
- the full `complete_biomamba.py` assembly
- the full training logic from `main_biomamba_pipeline.py`

They may become interesting later, but they are not the clean path to a scientifically interpretable Raman branch.

## Definition of Done for This Ticket Bundle

This bundle is complete when the repo has:

1. a multi-taper Raman frontend;
2. a patch-based FFT / wavelet Raman tokenizer;
3. a lightweight spectral-sector MoE classifier;
4. XAI adapters that can explain those modules at physically meaningful units.

At that point the Raman branch will have absorbed the best ideas from the external signal-analysis codebase without importing its unnecessary architectural complexity.
