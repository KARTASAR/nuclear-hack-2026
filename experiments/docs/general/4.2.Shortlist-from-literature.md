# Shortlist решений под наш проект (на базе обзора статей)

Этот файл переводит обзор литературы в прикладные варианты, которые стоит запускать на наших данных в первую очередь.

## 1) Что берём как «базу по умолчанию»

Базовый preprocessing-контур:

1. despike/cosmic-ray removal;  
2. Savitzky–Golay smoothing;  
3. baseline correction (`airPLS` или `arPLS`);  
4. normalization (`SNV`/`MSC`/`EMSC` в сравнении);  
5. harmonization wave-grid (интерполяция на общий grid).

Почему: это самый повторяемый и реалистичный путь из публикаций для биомед Raman.

## 2) Приоритетные варианты реализации (оценка 0–10)

Оценка учитывает: качество, риски leakage, объём внедрения в текущий код.

### Вариант A. `center1500` отдельно + point-level + group split по `mouse`

Суть:

- берём окно `center1500`;
- sample = точка `(X,Y)` (а не только усреднение карты);
- валидация строго по животному.

Оценка: **8.5/10**

Почему высокий приоритет:

- даёт максимум данных;
- соответствует практике patient-wise/subject-wise split;
- технически реализуем без радикальной перестройки архитектуры.

Риск:

- нужен аккуратный контроль leakage и объёма данных.

### Вариант B. Два независимых пайплайна (`center1500` и `center2900`) + ансамбль вероятностей

Суть:

- строим две модели отдельно на каждом окне;
- объединяем на уровне вероятностей/логитов.

Оценка: **9/10**

Почему:

- учитывает физически разные окна без насильной склейки;
- устойчивее к несовпадениям wave-grid;
- хорошо масштабируется по экспериментам.

Риск:

- больше orchestration и учёта артефактов при объединении.

### Вариант C. Сшивка двух окон в единый вектор (после интерполяции/матчинга)

Суть:

- строим единый feature-space из `1500 + 2900`.

Оценка: **7.5/10**

Почему ниже:

- потенциально сильный вариант по информации;
- но выше риск ошибок при матчинге пар и обработке аномалий в именах/файлах.

### Вариант D. Только file-level усреднение карты + классический ML baseline

Суть:

- одна карта -> один mean spectrum;
- быстрый SVM/LightGBM multiclass baseline.

Оценка: **7/10**

Почему нужен:

- очень быстрый sanity-check и точка отсчёта.

Ограничение:

- теряется spatial-структура карты.

### Вариант E. End-to-end single-step preprocessing (DL)

Суть:

- часть preprocessing учится моделью (по аналогии с single-step подходами).

Оценка: **5.5/10**

Почему пока ниже:

- интересно научно, но рискованно по времени и стабильности для хакатона.

## 3) Какие варианты лучше запускать первыми

Рекомендуемый порядок:

1. `D` как быстрый baseline (проверка пайплайна и метрик).  
2. `A` как основной надёжный рабочий вариант.  
3. `B` как наиболее перспективный по качеству.  
4. `C` только после стабилизации `A/B`.  
5. `E` — если остаётся время на R&D.

## 4) Ключевые правила из литературы, которые нельзя нарушать

1. Не делать случайный split по спектрам, если один и тот же объект может оказаться и в train, и в test.  
2. Сравнивать preprocessing-цепочки как гиперпараметры, а не фиксировать один метод «на веру».  
3. Отдельно учитывать инструментальный drift и сдвиги wave.  
4. Проводить оценку на multiclass-метриках (macro-F1, balanced accuracy, confusion matrix).

## 5) Итог в одном абзаце

По итогам внешнего обзора наиболее прагматичный курс: запускать классический preprocessing (SG + airPLS/arPLS + SNV/MSC/EMSC), делать group-wise split по животному, обучать сначала раздельные модели по `center1500/center2900`, и только затем тестировать более сложные схемы объединения или end-to-end preprocessing.
